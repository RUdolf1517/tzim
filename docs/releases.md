# Releases

Related: [roadmap](roadmap.md) · [benchmarks](benchmarks.md) · [dependencies](dependencies.md)

## 1. Versioning

The project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html), with the usual pre-1.0
allowance: a **minor** release may add formats and options, a **patch** release only fixes defects.

What is a breaking change here is not the command line but the *contract*. Removing a preservation
guarantee, narrowing what a format preserves, or changing the guarantee class of an existing handler
requires a major version. Adding a format, refusing a construct that used to be rewritten, or turning down
a candidate that used to be accepted are all minor changes — they only ever make the tool decline more work,
never lose more information.

`tzim --version` prints the crate version. The binary has no self-update mechanism and never checks for
network access.

## 2. What a release contains

| Artifact | Target | Notes |
| --- | --- | --- |
| `tzim-x86_64-unknown-linux-musl.tar.gz` | `x86_64-unknown-linux-musl` | statically linked, no libc dependency, runs on any Linux with a 3.2+ kernel |
| `tzim-aarch64-unknown-linux-musl.tar.gz` | `aarch64-unknown-linux-musl` | ARM64 servers and single-board computers; same static musl build, cross-linked with the toolchain's `rust-lld` |
| `tzim-aarch64-apple-darwin.tar.gz` | `aarch64-apple-darwin` | Apple silicon |
| `tzim-x86_64-apple-darwin.tar.gz` | `x86_64-apple-darwin` | Intel Macs |
| `tzim-x86_64-pc-windows-msvc.zip` | `x86_64-pc-windows-msvc` | needs the Visual C++ 2015–2022 redistributable, which Windows normally has |
| `tzim_amd64.deb`, `tzim_arm64.deb` | Debian, Ubuntu | the same static musl binary; the package declares no dependency at all |
| `tzim.x86_64.rpm`, `tzim.aarch64.rpm` | Fedora, RHEL | the same static musl binary |
| `SHA256SUMS` | — | one line per artifact |
| source archives | — | generated by GitHub from the tag |

Every archive contains the executable `tzim` (`tzim.exe` on Windows) built with `--release` and default
features. The default feature set covers the standard published handlers; **FITS is deliberately not compiled
into these archives** and requires a separate `--features fits` build as well as `--fits-tile` at run time.
The POSIX archives also carry `man/tzim.1`, `completions/` (bash, zsh, fish) and `LICENSE`. That is what the
Homebrew formula and the Linux packages install, so all four channels describe the same program — a man page
that disagreed with `--help` would be a second source of truth, and this project does not keep one.
`tests/packaging.rs` fails when an option in `--help` is missing from the man page or from any completion. The
fuzz entry points are behind a `fuzz-api` feature that no release enables; `--all-features` would put them in
the binary. JPEG still has to be enabled at run time with `--formats jpeg`.

Asset names are the Rust target triples and carry no version. That is deliberate: it makes
`https://github.com/RUdolf1517/tzim/releases/latest/download/<asset>` a stable URL, which is what
`install.sh` and the Homebrew formula download from. The `.deb` and `.rpm` are built by
`packaging/linux-packages.sh` from the Linux tarball with [nfpm](https://nfpm.goreleaser.com/), so the two
cannot describe the same binary differently.

Builds run on the platform's own GitHub-hosted runner, except the Linux binary, which is cross-compiled to
musl. Nothing is built on a developer machine: the development sandbox has no Rust toolchain, so the
release workflow is the only place a shipped binary is produced.

### 2.1 Install channels

| Channel | Platforms | Command |
| --- | --- | --- |
| shell script | Linux x86_64 and aarch64, macOS arm64 and Intel | `curl -fsSL https://raw.githubusercontent.com/RUdolf1517/tzim/main/install.sh \| sh` |
| Homebrew | macOS arm64, Linux x86_64 | `brew tap RUdolf1517/tzim https://github.com/RUdolf1517/tzim` then `brew install RUdolf1517/tzim/tzim` |
| apt | Debian, Ubuntu (amd64, arm64) | `curl -fsSLO .../releases/latest/download/tzim_amd64.deb` then `sudo apt install ./tzim_amd64.deb` |
| dnf | Fedora, RHEL (x86_64, aarch64) | `curl -fsSLO .../releases/latest/download/tzim.x86_64.rpm` then `sudo dnf install ./tzim.x86_64.rpm` |
| cargo | anything with Rust 1.88+ | `cargo install --git https://github.com/RUdolf1517/tzim` |
| archive | everything else | unpack the tarball or zip, put `tzim` on `PATH` |

`install.sh` prefers the prebuilt binary and falls back to `cargo install --git` when the platform has no
published build, so it never guesses a wrong binary.

**It verifies what it downloads.** The archive is checked against the release's `SHA256SUMS` before it is
unpacked, and a mismatch aborts the install with both hashes printed — it does not fall back to building from
source and hope. The installed binary is then run once (`--version`) before the script reports success, and
with `TZIM_VERSION` set the reported version has to match the one that was asked for. A `curl | sh` installer
that trusts the network path more than it trusts the project's own checksums would be a strange thing to ship
next to a program whose entire argument is that claims should be checked.

`TZIM_VERSION`, `TZIM_INSTALL_DIR`, `TZIM_REPO` and `TZIM_BRANCH` adjust what it does. `TZIM_BASE_URL` points
the download at a mirror, which is how an air-gapped machine installs this: the layout is `<base>/<asset>` and
`<base>/SHA256SUMS`, and the checksum check is not optional there either. `TZIM_INSECURE=1` skips it, prints a
warning, and exists for a mirror that publishes binaries but not hashes — an explicit, documented risk rather
than a silent one.

## 3. Verifying a download

```sh
sha256sum -c SHA256SUMS          # or: shasum -a 256 -c, on macOS
tar xzf tzim-x86_64-unknown-linux-musl.tar.gz
./tzim --version                 # prints tzim <version>
./tzim --list-formats            # lists the handlers compiled into this binary
man ./man/tzim.1                 # the manual page, if you want it before installing
```

The Linux packages and the Homebrew formula install that man page and those completions, so
`man tzim` and tab completion work after a package install, not only after reading the tarball.

`tzim --list-formats` is the honest answer to "what does this build actually support": it is generated from the
same table the documentation is checked against, so a format that is not compiled in cannot appear there.

Optional sanity check on your own data: run `tzim --dry-run -r <dir>` first. It performs every
step except the final rename, so it reports exactly what would change and proves the parser accepts your
files before anything is touched.

## 4. What is deliberately not provided

- **No MSI, no `.exe` installer, and no Windows package manager.** Windows gets the release zip: unpack it
  and put `tzim.exe` on `PATH`. Nothing is written outside the directory you unpack into, and there is no
  manifest in this repository standing in for a package that was never submitted.
- **No AUR, Snap, Flatpak, Chocolatey or Nix packages.** Each is a second source of truth about how the
  binary is built and packaged, and this project would rather have fewer of them than stale ones.
- **No crates.io publication yet.** The crate is packaged and built from the package in CI (`cargo package`),
  so `cargo install tzim` is one `cargo publish` away rather than a rewrite, but the publication itself needs
  a registry token and a decision about what a 1.0 crate name means. Until then the cargo channel is
  `cargo install --git`.
- **No Homebrew bottle, no distro repository.** The tap builds nothing: it unpacks the published tarball,
  so the bytes are the ones in `SHA256SUMS`.
- **No automatic updates and no telemetry.** The binary opens no sockets.
- **No `Cargo.lock` in the source archive before v0.4.0.** The lockfile is generated by CI
  (`.github/workflows/lockfile.yml`) because no developer machine in this project can run `cargo`; it is
  committed on `main` and included in later tags.
- **v0.4.1 shipped nothing a user can observe.** It added the real-file corpus, the fuzz targets and the
  comparative benchmarks; the binary was the same code as 0.4.0.
- **v0.4.2 changes packaging, not behaviour.** Same binary content, new asset names, plus `.deb`, `.rpm`,
  `install.sh` and the Homebrew formula.
- **v0.5.0 changes the command line, not the bytes.** `tzim optimize <path>` became `tzim <path>`, and
  `-i`, `--list-formats` and `--check-deps` were added. The old verb is still accepted, so upgrading never
  breaks a script; it is simply undocumented. The formula for 0.5.0 was pinned in a follow-up PR from the
  hashes in the release notes, which is the only order that never publishes a hash for a file that does not
  exist yet. v0.6.0, v0.7.0, v0.7.1, v0.8.0 and v0.9.0 follow the same order.
- **v0.10.0 changes the claims, not the bytes.** No handler was touched: the corpus writes the same total, the
  contracts and the refusals are unchanged. What changed is that CI now runs the jobs `docs/testing.md` had
  been listing (`msrv`, `fmt`, `deny`, `audit`), that every build is `--locked`, that the comparative
  benchmarks are this release's rather than v0.4's, that the progress line is drawn by `indicatif` instead of
  by hand, and that the README opens with the contract instead of with a directory of links.
- **v0.9.0 adds one format and refuses another.** zlib joins the handlers at a cost of 4 KiB of binary;
  FLAC is refused after measurement rather than carried in the queue, and the queue itself is now empty.
- **v0.8.0 changes the interface, not the work.** Colour, a progress line and four fixes found by the
  conformance audit; no handler changed, and the corpus writes the same bytes. It is also the first release
  whose binary grew for something other than a format (+20 KiB).
- **v0.7.1 is a build change.** The same source, compiled with a smaller optimisation level for this crate
  and full optimisation kept for the codecs, produces a binary 124 KiB smaller that writes byte-identical
  output. Nothing was removed, and the corpus proves it: 379 177 bytes written before and after.
- **v0.6.0 and v0.7.0 add flags and formats, not changes.** `--strip-metadata` is opt-in and off by default;
  TIFF joins the handlers. Neither release changes the output of a command that worked before.

## 5. Release process

1. `ci` must be green on `main`, including all three operating systems.
2. The version in `Cargo.toml` and the top `CHANGELOG.md` section are updated in the same pull request.
3. A GitHub release is created from a tag on `main`. Publishing it triggers
   `.github/workflows/release.yml`, which builds the three archives and the two Linux packages,
   smoke-tests each binary (`--version`, `--list-formats`), and uploads everything with `SHA256SUMS`.
4. A follow-up pull request pins the artifacts: the SHA-256 of the macOS and Linux archives into
   `Formula/tzim.rb`, and every `version` field in it is bumped in the same commit. Until that commit lands,
   `brew install` serves the previous release — the tap never points at a version whose hashes are invented.
5. The release notes state plainly what the release does **not** do: which formats are refused, which
   guarantees are not claimed, and which numbers are unmeasured (see [benchmarks](benchmarks.md)).

A release is never cut from a red build, and artifacts are never uploaded by hand.
