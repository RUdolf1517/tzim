**Данные не портятся ни в одном проверенном сценарии.** Массив после `funpack` побайтово равен исходному для int16, int8, float32 (включая NaN с payload, `±0` и денормали) и для масштабированных образов; это проверено на реальных файлах, а не выведено из кода (§3.4).

## 2. Проверенные положительные результаты

### P-1. `GZIP_2`: направление перестановки верное. [С][З/М]
Конвенция v2.3 §2: старший байт каждого отсчёта первым, по порядку отсчётов, затем следующий байт и т.д. `shuffle()` (`src/formats/fits.rs:549-559`) делает ровно это; `funpack` декодирует float-кандидата и возвращает массив, побайтово равный исходному (`04-evidence/E05-candidates/06-funpack-float32_specials.exit` = 0, `E05-summary.json` → `array_identical: true`).

### P-2. Геометрия тайлов и дескрипторы соответствуют конвенции. [С][З/М]
`ZTILE1 = ZNAXIS1`, `ZTILEn = 1` — дефолтная укладка конвенции; `NAXIS2 = Π ZNAXISn (n≥2)`; дескрипторы `(length, offset)` big-endian по 8 байт; heap сразу за таблицей, `THEAP` не нужен. `fitsverify` не выдаёт ни одного замечания по всем кандидатам (`E05-candidates/01,03,05,07,09-*.exit` = 0).

### P-3. Роли primary/extension восстанавливаются. [С][З/М]
`ZSIMPLE = T` только для primary, `ZTENSION = 'IMAGE'` для расширения; пустой primary перед таблицей — как у `fpack`. `funpack` реконструирует ровно один HDU на место одного, массив совпадает.

### P-4. Неструктурные карточки копируются побайтово и в порядке. [К]
`write_tiled` (`:783-790`) добавляет `card.raw` для каждой неструктурной карточки; `check_tiled` (`:905-925`) сравнивает эти последовательности. Это подтверждено и внешне: все расхождения в §3.3 — только структурные карточки, ни одна пользовательская не потеряна.

### P-5. Внутренний `verify` сравнивает массив побайтово, без арифметики. [К]
`check_tiled` (`:990-1016`): каждый дескриптор проверяется на попадание в heap, каждый тайл разжимается, размер сверяется со строкой, при `BITPIX < 0` выполняется `unshuffle`, затем `array != before` по `Vec<u8>`. `NaN`/`-0.0` в этом сравнении не участвуют — сравнение байтовое.

### P-6. Каркас gzip и независимая проверка целостности. [К][З/М]
`gunzip_member` (`:590-620`) проверяет магию, CRC-32 через `crc32fast` (не тот код, что пишет `flate2`) и `ISIZE`. Мутация байта в CRC-трейлере ломает `funpack` (exit 158) и была бы поймана внутренней проверкой; см. §7.

### P-7. `ZNAME1='NOISEBIT'`/`ZVAL1=0` — не выдумка, но и не поведение `fpack`. [З/М]

Три писателя на одном float32-массиве (`04-evidence/E13-znmae.json`):

| писатель | `ZCMPTYPE` | `ZNAME1`/`ZVAL1` |
| --- | --- | --- |
| tzim (транскрипция) | `GZIP_2` | `'NOISEBIT'` / `0` |
| `fpack -g -q 0` | `GZIP_1` | нет |
| `fpack -g2 -q 0` | `GZIP_2` | нет |
| `astropy CompImageHDU(quantize_level=0)` | `GZIP_2` | `'NOISEBIT'` / `0` |

То есть tzim совпадает с **astropy**, а не с `fpack`; обе формы легальны и обе декодируются одинаково (`fitsverify` — 0 ошибок на всех четырёх). Это снимает подозрение в «выдуманных карточках», но **не** оправдывает текст `docs/guarantees.md:1034-1037`: lossless читается отсутствием `ZSCALE`/`ZZERO` (конвенция §4), а не этими карточками (D-3).

### P-8. Отказы по `CHECKSUM`/`DATASUM` и `Z*`-кодекам безопасны. [К]
HDU с этими карточками копируется байт в байт, а `verify` для некопированного HDU требует побайтового равенства (`:1063-1075`). Устаревшая контрольная сумма остаётся верной, потому что байты не менялись.

### P-9. Кандидат принимается `fitsverify` без замечаний. [З/М]
Пять кандидатов, включая float32 с NaN/`±0`/денормалями и файл с `SIMPLE = F`: `0 warning(s) and 0 error(s)`, exit 0.

### P-10. Кандидат полностью декодируется эталонным `funpack`. [З/М]
`funpack -C` → exit 0 для всех пяти кандидатов; массив побайтово равен исходному (16 384 байта float32 против 16 384 после реконструкции; 12 специальных битовых шаблонов на месте — таблица в `04-evidence/ANALYSIS.md`, §C).

### P-11. Требование §8.3 выполнимо: эталон проходит его дословно. [З/М]
`fpack -g -q 0` → `funpack -C`: заголовок **побайтово равен оригиналу**, 0 расхождений, и для int16, и для float32. То есть ворота не «слишком строгие»; их валит писатель.

### P-12. gzip-члены проходят эталонный декодер без замечаний. [С][З/М]
Совпадает с `deflateInit2(..., 15+16, ...)` в `zcompress.c` и с обратной проверкой CRC/ISIZE в `funpack`.

### P-13. `fpack` — не побитовый эталон для float. [З][П]

В этом окружении `fpack` 1.7.0 (та же сборка, что и всё остальное) **не сохраняет биты** float32-данных. На `float32_specials.fits` из 4096 пикселей меняются **4092**:

| что было | что стало | сколько |
| --- | --- | --- |
| денормали (`0x000003EE` … `0x807FFFFF`) | `0x00000000` | 4086 |
| `±inf`, qNaN, sNaN (payload) | `0xFFFFFFFF` | 5 |
| `−0.0` | `+0.0` | 1 |

**Слой установлен [З].** Минимальный контроль — восемь пикселей (`05-tools/cfitsio-roundtrip.c`, `E15-library-vs-fpack/`):

* та же библиотека `libcfitsio` того же коммита, вызванная через публичный API (`fits_set_compression_type(GZIP_2)` → `fits_create_img` → `fits_write_img` → чтение обратно), возвращает **все восемь значений побитово**: `00000001 807FFFFF 80000000 7FC00001 7F800000 FF800000 3F800000 7F7FFFFF` — `identical = yes`; записанный ею файл легален (`fitsverify` 0 ошибок) и действительно сжат (`ZCMPTYPE = 'GZIP_2'` в `BINTABLE`, HDU 2);
* `fpack -g2 -q 0` на тех же восьми пикселях меняет **6 из 8**: денормали → `00000000`, `−0.0` → `00000000`, `qNaN` и `±inf` → `FFFFFFFF`.

То есть теряет **сама утилита `fpack`**, не библиотека и не формат. `funpack` той же сборки декодирует поток tzim побитово точно (0 из 4096), а `astropy` через свой CFITSIO тоже точен (`E14-oracle-rule.json`, `04-evidence/ANALYSIS.md` §G). Почему `fpack` это делает — не установлено [П]; для ревью важно следствие, а не причина.

**Следствие для проверки:** эталоном побитового равенства float-массива может быть только собственный round-trip tzim (`fpack`/`funpack` тут не годится), и строка `array_identical: false` в `E06-summary.json` для float — это потеря `fpack` (настоящая), а не свойство формата.

## 3. Проверка по восьми направлениям

### 3.1. Соответствие стандарту и конвенции

Ссылки: **FITS Standard 4.0** (§4.4.1 — обязательные карточки и `END`; §6.2 — random groups, уравнение (4)); **Tiled Image Convention v2.3, 2 июля 2013** (§2 — `Z*`-карточки, дефолтная укладка, `ZEXTEND`, ограничение `1P`; §3 — масштабированные образы; §4 — отсутствие `ZSCALE`/`ZZERO` как признак lossless). PDF FITS 4.0 в песочнице недоступен, поэтому §4.4.1/§6.2 сверялись по опубликованному тексту и по v3.0 (формулировки идентичны) — [С] с этой оговоркой.

Кандидаты tzim: `fitsverify` — 0 ошибок и 0 предупреждений на всех пяти (P-9). Это структурное соответствие, но **не** проверка содержимого тайлов (§7).

### 3.2. `GZIP_1`/`GZIP_2`, перестановка, геометрия, дескрипторы, границы heap

| Что | Вердикт | Чем |
| --- | --- | --- |
| `GZIP_2` = старший байт первым | верно | [С] конвенция §2 + `funpack` (P-1) |
| `GZIP_1` для целых, `GZIP_2` для float | соответствует эталону | [З/М] `fpack -g` для int16 даёт `GZIP_1`, `-g2`/`-g -q 0` для float — `GZIP_2` |
| Укладка `ZTILE1 = NAXIS1`, `ZTILEn = 1` | верно | [С][З/М] |
| Дескрипторы `(u32 length, u32 offset)` | верно для heap < 2.1 ГБ | [С] конвенция §2, §4 |
| Границы heap в `verify` | проверяются (`:969-983`) | [К] |
| Потолок `1P` (2.1 ГБ) | **не проверяется**; код ограничивает 4 ГиБ через `u32::try_from` (`:684-687`) | [К][С] → F-06 |

### 3.3. Primary/extension, роли, прочие HDU, значимые карточки

Роли восстанавливаются правильно (P-3), прочие HDU копируются побайтово и это проверяется тестом `fits_every_other_hdu_is_copied_verbatim` (`tests/integration.rs:3541`).

**Но заголовок переписанного HDU не воспроизводится.** Сравнение 80-колоночных карточек (`04-evidence/ANALYSIS.md`, §D; сырые прогоны — `E07-headerdiff`):

| трасса | расхождений | что именно |
| --- | --- | --- |
| `fpack` → `funpack -C` (эталон), int16 | **0** | заголовок байт в байт |
| `fpack` → `funpack -C` (эталон), float32 | **0** | заголовок байт в байт |
| tzim → `funpack -C`, int16 | **4** | `EXTEND` потерян; комментарии `BITPIX`, `NAXIS`, `SIMPLE` заменены |
| tzim → `funpack -C`, float32 | **4** | то же |
| tzim → `funpack -C`, `EXTEND = F` | **4** | то же, причём теряется именно `EXTEND = F` — заявление «расширений нет» |

Дословно для int16:
```
lost     EXTEND  =                    T / FITS dataset may contain extensions
changed  BITPIX  = 16 / number of bits per data pixel   ->  16 / array data type
changed  NAXIS   =  2 / number of data axes             ->   2 / number of array dimensions
changed  SIMPLE  =  T / conforms to FITS standard       ->   T
```
Массив при этом во всех случаях идентичен. Это находка **F-03**.

### 3.4. Целые, масштабирование, плавающая точка, NaN, `±0`

Специальные значения float32 (16 384 байта массива, побайтовое сравнение до и после `funpack`):

| записано | смысл | после round trip |
| --- | --- | --- |
| `0x7F800000` | +inf | `0x7F800000` |
| `0xFF800000` | −inf | `0xFF800000` |
| `0x7FC00001` | qNaN, payload 1 | `0x7FC00001` |
| `0x7FC00002` | qNaN, payload 2 | `0x7FC00002` |
| `0x7FA00001` | sNaN, payload 1 | `0x7FA00001` |
| `0x00000000` | +0.0 | `0x00000000` |
| `0x80000000` | −0.0 | `0x80000000` |
| `0x00000001` | минимальный денормал | `0x00000001` |
| `0x807FFFFF` | максимальный отрицательный денормал | `0x807FFFFF` |
| `0x3F800000` / `0xBF800000` | ±1.0 | совпадают |
| `0x7F7FFFFF` | FLT_MAX | `0x7F7FFFFF` |

**Вывод [З/М]: формат сохраняет биты.** Это не следует путать с оракулом: `fits-oracle.py:363` сравнивает float через `np.array_equal(..., equal_nan=True)`, что **не различает payload NaN и знак нуля** — F-10 остаётся, но теперь как дефект *доказательства*, а не формата.

**Чью именно потерю видит `equal_nan`.** Тот же прогон даёт отрицательный контроль: файл, отличающийся от оригинала одним payload NaN (`0x7FC00002` → `0x7FC00001`), проходит собственную функцию ворот `check_rewritten` с **0 замечаний**, хотя побайтовое сравнение тех же массивов даёт `False` (`E14-oracle-rule.json` → `nan-repayload`). То есть маскировка — не гипотеза, а воспроизведённый результат.

**И почему эталон `fpack` для float не годится [З].** Четыре писателя на одном массиве, все декодированы `funpack` той же сборки:

| писатель | отличий из 4096 | нефинитные | денормали | `−0.0` |
| --- | --- | --- | --- | --- |
| tzim (транскрипция, `GZIP_2`) | **0** | 0 | 0 | 0 |
| `fpack -g -q 0` | 4092 | 5 | 4086 | 1 |
| `fpack -g2 -q 0` | 4092 | 5 | 4086 | 1 |
| `astropy CompImageHDU(GZIP_2, q=0)` | **0** | 0 | 0 | 0 |

Подробности — P-13, включая минимальный контроль на восьми пикселях: `libcfitsio` того же коммита через свой API возвращает их побитово, а `fpack` — нет. Практический вывод: **нельзя строить побитовое сравнение float-массива на выходе `fpack`** — оно покраснеет на корректном файле tzim и на корректном файле astropy.

Масштабирование (`BSCALE`/`BZERO`) — см. F-05: карточки переносятся дословно, значения восстанавливаются (`32768, 32769, …` для uint16; `−100.0, −97.5, …` для `BSCALE = 2.5`), но *решение* о отказе зависит от формата карточки.

### 3.6. Независимость проверки от писателя

Внутренний `verify` использует **тот же** `scan()` и `decide()`, что и писатель, и проверяет самосогласованность: разожми тайлы тем же `unshuffle` и сравни с исходным массивом. Поэтому **симметричная** ошибка (например, перестановка «младший байт первым» вместе с обратной `unshuffle`) пройдёт внутренний `verify` беспрепятственно: он вернёт исходные байты. Такая ошибка ловится только внешним читателем.

Что реально проверяет внешняя пара (см. §7 и `E05`):

| ошибка писателя | внутренний `verify` | `fitsverify` | `funpack` + сравнение байтов |
| --- | --- | --- | --- |
| инвертированная перестановка `GZIP_2` | **пропустит** | пропустит | **поймает** |
| неверная геометрия тайлов | поймает (`ZTILE1`/`ZTILEn` сверяются, `:895-903`) | иногда | иногда |
| испорченный payload тайла | поймает (CRC+сравнение) | **пропустит** | **поймает** |
| потерянная/изменённая карточка | поймает только неструктурную | **пропустит** | поймает только diff |

Отсюда: зелёный `fitsverify` **не является** свидетельством о содержимом; единственная независимая проверка данных — `funpack` + побайтовое сравнение, и она обязана быть в воротах (§7).

### 3.7. Достаточность плана #71

Разобрано в §7: что именно доказывают `fitsverify` и `funpack`, чего не доказывают, и какие отрицательные контроли обязательны. Главный результат прогона: `fitsverify` **не распаковывает тайлы** и не замечает ни одного из семи видов порчи данных, которые замечает `funpack`.

### 3.8. Требование «буквального diff»

Разобрано в §9. Требование реалистично и выполняется эталоном; текущая формулировка ворот требует двух уточнений (`funpack -C` и сравнение полных 80 колонок).

### 4.5. F-05 — отказ по `BSCALE`/`BZERO` зависит от формата карточки

**Severity: Medium; нужно решение владельца.**
**Где:** `src/formats/fits.rs:119-124` (`Card::int` = `text.parse::<i64>()`), используется в `:493-499`.
**Нарушено:** FITS 4.0 §4.4.1 — `BSCALE`/`BZERO` имеют тип floating point; легальны `1.0`, `32768.0`, `2.5`, `3.2768E4`. Контракт (`docs/guarantees.md:1068`) требует «`BSCALE = 1` and `BZERO = 0`» как необходимое условие, и `:1125` перечисляет неидентичное масштабирование в отказах.

* `BSCALE = 1 / BZERO = 32768.0` (uint16-конвенция): решение — `Tile`, кандидат легален, `funpack` даёт тот же массив, `astropy` читает **те же uint16-значения** `[32768, 32769, …]` (`E10-scaling/05-astropy-values.stdout`).
* `BSCALE = 2.5 / BZERO = −100.0` (настоящее перемасштабирование): решение — `Tile`, хотя контракт требует отказа; `astropy` читает `[−100.0, −97.5, …]` и до, и после.
* Для сравнения: `BZERO = 32768` (целое) отказ вызывает — это и проверяет `a_scaled_image_is_refused` (`:1223-1230`), и фикстура оракула `scaled.fits`.

**Влияние.** Один и тот же физический образ обрабатывается по-разному в зависимости от форматирования карточки. Данные не портятся: карточки переносятся дословно (`E10-scaling.json` → `table-cards-*`), значения совпадают.

**Исправление — выбрать одно, не оставлять как есть.**
**(а) Консервативное:** разбирать значение как `f64` и отказывать при `!= 1.0 / 0.0`. Минимальная правка, соответствует нынешнему тексту контракта.
**(б) По конвенции:** принимать масштабированные образы (v2.3 §3: «should normally be compressed without any further scaling, and the `BSCALE` and `BZERO` keywords should be copied verbatim»), убрать их из списка отказов и добавить проверку, что `ZSCALE`/`ZZERO` **не появились**. Прогон показывает, что (б) безопасно: массив и карточки сохраняются.
**Проверка.** Фикстуры `bzero_float.fits` и `bscale_two_five.fits`: при (а) — `skipped`/exit 0 с причиной; при (б) — переписывание с сохранением карточек и отсутствием `ZSCALE`/`ZZERO`.

## 7. Что доказывают `fitsverify` и `funpack` (и чего не доказывают)

Основано на 19 мутациях реального кандидата (`bundle/02-transcription/exp_mutations.py`; сырые stdout/stderr/exit — `04-evidence/E08-mutations/`, сводка — `04-evidence/ANALYSIS.md` §F).

| мутация | `fitsverify` | `funpack` | файл создан | массив = оригинал |
| --- | --- | --- | --- | --- |
| без изменений | 0 | 0 | да | да |
| байт в DEFLATE (+40/+60/+120/+200) | **0** | **158** | нет | — |
| CRC-32 трейлера | **0** | **158** | нет | — |
| `ISIZE` трейлера | **0** | **158** | нет | — |
| CM gzip 08→09 | **0** | **158** | нет | — |
| длина в дескрипторе строки 0 | **1** | 0 | да | да |
| `ZTILE1` 256→128 | **0** | **0** | да | **да** |
| `ZSIMPLE` T→F | **0** | 0 | да | да |
| `EXTNAME` переименован | 0 | 0 | да | да |
| `ZCMPTYPE` ← `RICE_1` | 1 | 202 | нет | — |
| `ZBITPIX` ← `-32` | 1 | 151 | нет | — |
| `NAXIS2` 256→255 | 1 | 158 | нет | — |
| `ZNAXIS2` 256→255 | 1 | 158 | нет | — |
| `ZTILE2` 1→2 | 1 | 158 | нет | — |
| `ZNAXIS1` 256→128 | 1 | 158 | нет | — |
| файл обрезан на запись | **2** | 0 | да | **нет** |

**Выводы [З/М]:**

1. **`fitsverify` не распаковывает тайлы.** Ни один из семи видов порчи данных (байт payload, CRC, ISIZE, метод сжатия) он не замечает. Он проверяет согласованность метаданных и целостность файла — это линт заголовка, а не проверка изображения.
2. **`funpack` действительно декодирует** и на порче данных падает без создания файла.
3. **Ни один из двух не полон в одиночку:** обрезанный файл `funpack` «распаковывает» с exit 0, но массив при этом **другой** — то есть `funpack` без побайтового сравнения бесполезен. Комбинация «`funpack` + сравнение байтов» — единственная проверка содержимого.
4. **`ZTILE1` может быть неверным, и никто этого не заметит** (ни `fitsverify`, ни `funpack`, ни сравнение массива) — важен только дескриптор строки. Это дополнительный аргумент, что §8.3 должен сверять заголовок, а не только массив.

**Обязательные контроли (обновлены после прогона):**

* **C-1.** Битый байт в heap → **должен краснеть шаг `funpack`**; `fitsverify` на этом файле остаётся зелёным. Контроль, ждущий ненулевого кода от `fitsverify`, будет **ложно зелёным**.
* **C-2.** Испорченный CRC-трейлер → `funpack` падает и не оставляет файла.
* **C-3.** Инвертированная перестановка `GZIP_2` → сравнение массивов обязано упасть (внутренний `verify` этого не увидит — §3.6).
* **C-4.** Положительный контроль: `fpack -g [-q 0]` → `funpack -C` на той же фикстуре даёт **пустой** diff заголовка. Проверено: даёт. **Ограничение:** только заголовка. Побитовое сравнение **массива** с выходом `fpack` для float недопустимо — `fpack` сам теряет денормали, нефинитные и `−0.0` (P-13).
* **C-5.** Фикстура с ровно одной ожидаемой разницей → разница должна быть **названа**, а не «нормализована».
* **C-6.** Файл, который tzim отказал → `skipped`, exit 0, файл побайтово тот же, причина названа.
* **C-7.** `fitsverify` на заведомо плохом файле → ненулевой код (у нас: обрезанный файл, exit 2).
* **C-8.** `funpack` без сравнения массивов ничего не доказывает: обрезанный файл даёт exit 0 и неверные данные. Сравнение обязательно.
* **C-9 (новый).** Негативный контроль `equal_nan`: кандидат с изменённым payload NaN **обязан** краснеть. Сейчас проходит зелёным (F-10, `E14-oracle-rule.json`).
* **C-10 (новый).** Негативный контроль правила кодека: легальный float-файл с `GZIP_1` (например, из `fpack -g -q 0`) **не должен** считаться дефектом, если оракул назван проверкой конвенции. Сейчас краснеет (F-11).

## 9. Контракт «буквального diff восстановленных заголовков» — точная формулировка

**Требование реалистично и ослаблять его не нужно.** Эталонная пара (`fpack -g [-q 0]` → `funpack -C`) воспроизводит заголовок **побайтово** на обоих проверенных входах (int16 и float32 со специальными значениями): 0 расхождений. Разница, которую даёт текущий писатель (4 расхождения), — дефект писателя, а не строгости ворот.

**Единственная реальная поправка — флаг `-C`.** `funpack` без `-C` **всегда добавляет** `CHECKSUM` и `DATASUM` в восстановленный HDU (проверено: `E09-gate`, `reference-no-C` → 2 расхождения, при том что вход их не имел). С ними diff непуст у кого угодно.

**Точная формулировка (замена нынешней, без ослабления).** Пусть `O` — заголовок исходного HDU (последовательность 80-колоночных карточек без `END`), `R` — заголовок того же HDU, восстановленный `funpack -C` из кандидата.

1. **`R` совпадает с `O` побайтово, карточка в карточку, в том же порядке.** Никаких исключений: ни структурных, ни «сгенерированных», ни комментариев.
2. Для HDU, которые не переписывались, — побайтовое равенство всего HDU (уже есть).
3. Если `funpack` запускается без `-C`, allowlist — **ровно** `{CHECKSUM, DATASUM}`, и тест обязан падать при появлении третьей карточки (C-5). Предпочтительно — `-C` и пустой allowlist.
4. Сравнение — по **полным 80 колонкам**, включая комментарий. Сравнение только колонок 11–30 (как сейчас в PR #73, `cards_of`) этому контракту не соответствует: оно пропускает 3 из 4 расхождений F-03 (§10).

Обоснование: п.1 — это дословно требование конвенции v2.3 §2 («a verbatim copy of the value and comment fields … to reconstruct an identical copy of the original FITS file»), и эталон его выполняет; п.3 фиксирует то, что добавляет сам инструмент, и при `-C` пуст.

**Чего делать нельзя:** сравнивать `funpack(tzim_output)` с `funpack(fpack(original))`. Diff станет пустым и перестанет что-либо доказывать о сохранении заголовка; эталонный писатель тоже может потерять карточку, и «эталон» её замаскирует.

## 13. Что потребуется для отдельного ревью после исправлений

Ревью исправлений будет **отдельным** и **на фактических результатах tzim**, а не на транскрипции. Чтобы его можно было провести, к новому коммиту `SHA₂` нужно приложить:

1. **Собранный бинарь и версию**: `SHA₂`, `cargo build --features fits --release`, вывод `tzim --version`, sha256 бинаря.
2. **Прогоны `cargo test`** целиком (stdout + exit) — особенно новые негативные тесты F-07/F-08.
3. **Файлы, а не описания:** входы, кандидаты и реконструкции для фикстур F-01, F-02, F-03, F-05 (по одной на каждую ветку), с sha256.
4. **Результаты внешних инструментов** на этих кандидатах: `fitsverify -l` (stdout+exit), `funpack -C` (stdout+exit), сравнение реконструированного заголовка с оригиналом **по 80 колонкам** и массивов **побайтово**.
5. **Зелёный прогон ворот #71** после N-1/N-2 — то есть с `funpack -C` и с полным сравнением колонок, плюс отчёт, что он падает на испорченном кандидате (контроли C-1/C-2/C-3), на подменённом payload NaN (C-9) и что легальный `GZIP_1`-float не считается дефектом, если оракул называется проверкой конвенции (C-10).
6. **Ответы на пять вопросов §11** — иначе часть выводов нельзя проверить: они зависят от того, что считается контрактом.

До этого момента позиция ревью: **выпускать `fits` нельзя**; блокеры B-1…B-4 открыты, ни один не закрыт документацией.
