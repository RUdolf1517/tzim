#### 4.2.1 Что именно сделали эталонные писатели с float-кандидатом (`03-evidence/reference-writer-diff.stdout`)

`fpack -g2 -q 0` пишет `ZCMPTYPE='GZIP_2'`, `ZQUANTIZ='NONE'`, `ZBLANK=-2147483647`, колонок `ZSCALE`/`ZZERO` **нет** — то есть по §4 конвенции файл заявлен как lossless. После `funpack` он отличается от оригинала **25 байтами** в пикселях 0–4, 6, 7, 8:

```
pixel 0   7f800000 -> ffffffff   inf  -> nan
pixel 1   ff800000 -> ffffffff   -inf -> nan
pixel 2   7fc00001 -> ffffffff   nan  -> nan   (payload изменён)
pixel 3   7fc00002 -> ffffffff   nan  -> nan
pixel 4   7fa00001 -> ffffffff   sNaN -> nan
pixel 6   80000000 -> 00000000   -0.0 -> 0.0
pixel 7   00000001 -> 00000000   наименьший положительный денормал -> 0.0
pixel 8   807fffff -> 00000000   наибольший отрицательный денормал -> 0.0
```

То есть в этой среде **этот записанный вызов `fpack`** не является lossless для inf/NaN/субнормалей/знака нуля, хотя заголовок обещает обратное. Это утверждение **только про записанный вызов в этой среде** (формулировка P-13), не про `fpack` вообще и не про `tzim`.

`imcopy 'out[compress GZIP_2]'` пишет `ZCMPTYPE='GZIP_1'` — запрошенный кодек **игнорируется** — и квантует с `ZQUANTIZ='SUBTRACTIVE_DITHER_1'`, `ZDITHER0=1669`, добавляя колонки `ZSCALE`/`ZZERO` (3 поля в строке вместо 1). В 63 строках из 64 `ZSCALE = 0.151317` (шаг квантования много меньше расстояния между соседними значениями исходника), в строке со спецзначениями `ZSCALE = NaN`. Итог: **10 388 различающихся байт**, пиксели 5–11 (`0.0`, `-0.0`, `1.0`, `-1.0`, денормалы, `FLT_MAX`) становятся `7fe00001` (NaN). Это свойство инструмента и этой фикстуры, не `tzim`.

* 32 фиксированных случая: `1`, `1.0`, `.1E1`, `10D-1`, `+1`, `0001.0000` → «единица»; `1.00000000000000001`, `0.9999999999999999999`, `1E+1`, `1D-400`, `1D+400`, `-1` → «не единица»; `-0`, `+0.000`, `0E+999999999999999999999` → «ноль»; `1E-999999999999999999999` → «не ноль»; синтаксически неверные → отказ;
* 200 000 случайных строк: **0 ложных «единиц»/«нулей»**, **0 отказов** от точной единицы/нуля.

Это проверка **алгоритма**, а не прогон Rust-кода; так и помечено. Дополнительно показано, чем опасен `f64`:

```
float('1.00000000000000001') == 1.0 : True
float('1E-400')              == 0.0 : True
float('1E+100')              == 1.0 : False
```

То есть два механизма ложного прохода — «округляется до 1.0» и «недополняется до 0.0» — реальны, и оба закрыты в коде `9de2b70` и в его негативном тесте (§6).

## 5. F-06: арифметическая граница (не прогон)

Конвенция, точная цитата — **Tiled Image Convention v2.3, 2 July 2013, §3 (Columns), замечание о variable-length columns**:

> «The COMPRESSED DATA, GZIP COMPRESSED DATA, and UNCOMPRESSED DATA columns … will normally use the '1P' variable-length array FITS column format if the size of the heap in the compressed FITS file is less than about 2.1 GB in size. If the heap is larger than 2.1 GB, then the '1Q' format (which uses 64-bit pointers) must be used.»

(В прежнем пакете это правило было отнесено к §2; правильно — §3. Это уточнение ссылки, не пересмотр находки.)

Код `9de2b70` в этой части не изменён: `TFORM1` всегда `1PB({longest})` (`fits.rs:884`), смещение и длина каждого члена — `u32` (`:854`, `:856`). Отсюда **арифметика**, без всякого прогона:

* `u32::try_from` не даёт записать смещение `>= 2^32 = 4 294 967 296` байт → heap физически ограничен `[0, 4 GiB)`.
* Правило конвенции требует `1Q` при heap `> 2.1 GB ≈ 2 147 483 648` байт. Значит, **окно несоответствия** — `2 147 483 648 < heap ≤ 4 294 967 295` байт: файл пишется с `1PB` и нечитаем теми, кто соблюдает §3.
* Чтобы попасть в это окно, нужен heap > 2 147 483 648 байт. Для несжимаемых данных heap ≈ размер массива, поэтому достаточно:
  * `BITPIX=16`: ≥ `2 147 483 648 / 2 = 1 073 741 824` пикселя (2 GiB данных);
  * `BITPIX=-32`: ≥ `536 870 912` пикселей (2 GiB данных);
  * для хорошо сжимаемых данных порог выше во столько раз, во сколько gzip сжимает.
* Ни один такой файл здесь не создавался; **это арифметическая граница, а не прогон файла > 2 ГБ**.

Статус F-06: **`not run`**. Формулировка «код допускает heap до 4 ГиБ и всегда пишет `1PB`» — чтение кода, подтверждённое арифметикой, но не прогоном.

Старая ожидаемая строка после диффа **не** прошла бы, новая до диффа — тоже. Это чтение кода и байтов фикстуры, **не прогон**; всё, что касается решений `tzim`, остаётся `not run`.

**Что именно закрывает новое сравнение `BSCALE`/`BZERO` (чтение кода `5dd45b3`).** Старая проверка была не просто «целочисленной»: `header.int("BSCALE").unwrap_or(1)` возвращает `None` для любого нецелого значения, а `unwrap_or(1)` превращает это в **единицу**. То есть `BSCALE = 1.5` без `BZERO` не попадал в отказ: документально заявленная политика «масштабированные образы отклоняются» не покрывала десятичные написания. Новый код на неразбираемое или не-единичное значение **отказывает** (`decimal_is_one(...) != Some(true)`), и отказ становится полным.

Важная оговорка, чтобы это не прочитали как заявление о потере данных: **потери здесь не было** — карточка `BSCALE`/`BZERO` не структурная и копируется в таблицу дословно, поэтому читатель применил бы ровно тот же масштаб. Речь о **дыре в политике отказа**, а не о порче пикселей; и именно поэтому владелец требовал точной классификации, а не «примерно единицы».

Покрытие тестами: `rounded-one` (`BSCALE = 1.00000000000000001`) на старом коде тоже прошёл бы (тот же `int()` → `None` → 1), так что этот тест ловит и старую дыру, и `f64`-ложный проход. Но самого простого случая — `BSCALE = 1.5` — в списке нет; он отвергается новым кодом по построению, и его стоит добавить одной строкой.

**Негативные тесты в диффе.** Добавлено 5 тестов: random-groups (отказ), `SIMPLE=F` (отказ), структурные Z-формы (успех + побайтовые сравнения), десятичная единица (успех), не-единичный масштаб (три отказа: `1.00000000000000001`, `1D-400`, `1E+100`). ## 7. Новые замечания (не блокеры, кроме O-1 для CI-диагностики)

**O-1 (Low, ворота).** `check_candidate` не ловит `ValueError` из собственного `parse`: 3 из 26 испорченных кандидатов (`PCOUNT`, `BITPIX`, `GCOUNT`) дают traceback вместо вердикта (`fits-heasarc.py:1186` → `:285`/`:313`). Поведение fail-closed (CI краснеет, приёмки нет), но диагностика — трейсбек, а не записанный отказ. Лечится `try/except ValueError` вокруг `parse` с вердиктом «candidate does not parse».

**O-2 (Low, `check_tiled`).** Остаток F-08: не сверяются `TFORM1`, `ZNAME1`/`ZVAL1`, сгенерированный `EXTNAME` (когда в исходнике его нет), `XTENSION`/`BITPIX`/`NAXIS`/`GCOUNT`/`TFIELDS` таблицы, отсутствие `ZSCALE`/`ZZERO`, `THEAP`. Прогон показывает, что порча `ZVAL1` проходит и внешние контроли (§4.7). Рекомендация прежняя: по одному негативному тесту на строку.

**O-3 (Info, `structural()`).** Карточка исходника с именем из структурного набора не копируется и не замечается (§3.3). Конвенция v2.3 §2 «Other Keywords» это только «recommends». Код не новый.

**O-4 (Info, инструменты).** В этой среде `fpack -g2 -q 0` и `imcopy … [compress]` меняют биты float-массива, а `imcopy` игнорирует запрошенный кодек (§4.2.1). Утверждение ограничено записанными вызовами (P-13); на `tzim` не переносится.

**O-5 (Info).** `ZPCOUNT`/`ZGCOUNT` пишутся, если карточки есть в исходнике, без проверки, что исходник — `IMAGE`-расширение; §2 конвенции разрешает их «only … if the original uncompressed image was contained in an IMAGE extension». Достижимо только для нестандартного primary с `PCOUNT`/`GCOUNT` (random groups отклоняются), поведение не новое.
