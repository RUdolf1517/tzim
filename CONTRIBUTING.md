# Contributing

Thanks for considering a contribution. This project has one rule that outranks everything else:

> **Tzim must never lose information, and must never claim a guarantee it cannot verify.**

That rule decides most review outcomes before any style question comes up.

---

## 1. Before you write code

For anything larger than a typo:

1. Open an issue (bug report or format request).
2. For a new format, read [docs/formats.md](docs/formats.md#4-admission-criteria-for-a-new-format) — ten
   items, all mandatory.
3. Wait for agreement on the contract. Code written before the contract is usually thrown away, because the
   contract is what the reviewers check against.

No format may be advertised anywhere (README, release notes, `--help`) before its contract exists and its
tests pass.

---

## 2. Development setup

```sh
# Rust 1.88 or newer
rustup toolchain install 1.88
cargo build
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

Optional tooling:

```sh
cargo install cargo-deny cargo-audit cargo-bloat --locked
cargo deny check
cargo audit
```

Fuzzing uses nightly and lives in its own workspace member:

```sh
cargo install cargo-fuzz --locked
cd fuzz && cargo +nightly fuzz run png_reader
```

The build must work offline (`cargo build --offline`) and must not require a C compiler.

---

## 3. What a pull request must contain

| Change | Required in the same pull request |
| --- | --- |
| Bug fix | a regression test that fails before the fix |
| New format | contract in `docs/guarantees.md`, verification, fixtures, `T-*` tests, size measurement, README/roadmap update |
| New flag | `docs/cli.md` update, parser tests, integration test |
| New dependency | `docs/dependencies.md` entry answering the six questions, licence check, measured binary delta |
| Behaviour change | `CHANGELOG.md` entry |
| Anything touching replacement | tests for every affected failure mode in `docs/safety.md` |

Additionally:

- `cargo fmt` and `cargo clippy -D warnings` must be clean;
- CI must be green on Linux, macOS and Windows;
- the binary-size gate must pass, or the growth must be justified in the description;
- no new `unsafe` (the crate forbids it);
- no dependency added "to save lines of code".

---

## 4. Code style

- Idiomatic Rust, `rustfmt` defaults, edition 2024.
- Prefer plain functions and small enums over trait objects, generics and abstraction layers. If a new module
  needs a diagram to explain, it is probably too complex for this project.
- Errors are one `enum Error` with a `Display` implementation; no error-chain crates.
- No panics on input data. `unwrap`/`expect` are acceptable only for invariants that cannot fail, and must be
  commented as such.
- No `unsafe`. Ever. If a dependency needs it, that is a discussion, not a decision.
- Comments explain *why* (especially in the container writers); the code explains *what*.
- Keep the hot paths obvious: a reader should be able to verify the "copy everything except these bytes"
  property by reading the writer top to bottom.

---

## 5. Testing expectations

Every behavioural change needs a test. Specifically:

- contract clauses map to named tests (`T-PNG-03`, `T-ZIP-11`, …) listed in
  [docs/testing.md](docs/testing.md#2-traceability);
- corrupted and refusal cases are as important as success cases;
- tests must not touch the network, must not depend on the clock, and must clean up their temporary
  directories;
- fixtures stay small; large samples are generated by the scripts in `tests/fixtures/generate/`.

If you find a case where Tzim produced a file that a real consumer rejects, **that is the highest-priority
bug class in the project**. Please include the original file (or a minimised reproducer) and the consumer
that rejected the output.

---

## 6. Reporting bugs

Use the issue templates. For a suspected data-loss bug:

1. Stop using the affected version.
2. Do not run Tzim again on the same files (it may replace more of them).
3. If possible, keep the original bytes; the replacement is not reversible.
4. Open an issue titled `data loss: <short description>` with the exact command, the platform, the file type
   and size, and whether the original file was modified.

If a file was replaced and the output is valid but larger, or the original was changed despite an error
report, say so explicitly — that is a contract violation and is treated as critical.

---

## 7. Commit messages

Conventional Commits:

```
feat(png): re-select scanline filters
fix(zip): preserve central-directory extra fields
docs: specify the JPEG contract
test(gzip): cover FHCRC preservation
```

Keep the subject under 72 characters. Explain *why* in the body when the change is not obvious.

## 9. Review culture

Reviews here are about evidence, not preference. Expect questions like:

- Which contract clause does this implement, and which test proves it?
- What happens with a truncated file, a 4 GiB file, a non-UTF-8 path, a Windows rename failure?
- What is the size cost?
- Can this be refused instead of guessed?

Those questions are not hostility; they are the mechanism by which a file optimizer earns trust.
